# S09 — Notebook reproducibility

Sources: Rule et al., "Ten simple rules for writing and sharing computational
analyses in Jupyter Notebooks", *PLOS Computational Biology* 15(7), 2019
(`journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1007007`);
plus the Jupyter community `jupyter-guide` recommendations.

This is the angle most sample repositories miss, and the one that matters most for
a notebook-based artefact.

---

## Rule 1 — Tell a story for an audience

- **S09-C01** Every notebook opens with what it teaches, who it is for, and what the
  reader needs before starting.
- **S09-C02** Narrative explains *why*, not only *what*.
- **S09-C03** Every notebook ends with a conclusion or a next step, not a dangling
  final cell.
- **S09-C04** Depth is calibrated to a stated audience.

## Rule 2 — Document the process, not just the results

- **S09-C05** Non-obvious API behaviour discovered during development is documented
  in the notebook, not silently worked around.
- **S09-C06** Dead ends worth knowing about are recorded (e.g. "this parameter looks
  like it should work and returns 400").
- **S09-C07** No manual post-processing: everything a reader sees was produced by a
  cell in the notebook.

## Rule 3 — Use cell divisions to make steps clear

- **S09-C08** One meaningful step per cell.
- **S09-C09** Markdown heading above each logical section; headings form a coherent
  outline.
- **S09-C10** Cells stay under roughly one screen; a cell over ~100 lines is split.
  **Declared exception (one cell, repo-wide):** a single `class` body cannot be
  split across cells — Python raises `IndentationError`.
  `99-cross-cutting/02-migrating-from-openai.ipynb` holds one 147-line cell whose
  only top-level statement is the `MantleCompat` class. That class *is* the
  deliverable of the section: a reader copies it whole. Splitting it into a base
  class plus monkey-patched methods would be worse code taught for the sake of a
  metric. Every other cell in the collection is under 100 lines.
- **S09-C11** Heading hierarchy is well-formed — no skipped levels, single `#` title.

## Rule 4 — Modularize code

- **S09-C12** Repeated logic becomes a function, not a copy-pasted cell.
- **S09-C13** Genuinely shared machinery lives in an importable module.
- **S09-C14** Functions are defined before the cell that first calls them.

## Rule 5 — Record dependencies

- **S09-C15** A dependency manifest exists and is complete.
- **S09-C16** Versions are constrained.
- **S09-C17** Every imported package appears in the manifest; every manifest entry is
  actually used.
- **S09-C18** Setup instructions are executable as written.

## Rule 6 — Use version control

- **S09-C19** No generated artefacts committed: `__pycache__`, `.ipynb_checkpoints`,
  `.DS_Store`.
- **S09-C20** `.gitignore` covers the artefacts this project actually produces.
- **S09-C21** Notebook metadata is clean — no absolute local paths, no stray kernel
  specs pointing at a personal virtualenv.

## Rule 7 — Build a pipeline

- **S09-C22** Key parameters (Region, model ID) are declared at the top, not buried.
- **S09-C23** **Restart-and-run-all must succeed.** This is the central control: a
  notebook must execute top-to-bottom in a fresh kernel.
- **S09-C24** Execution counts are sequential from 1 with no gaps, proving the
  committed state came from one clean run.
- **S09-C25** No hidden state dependency — no cell that only works if an earlier
  deleted cell was run.
- **S09-C26** Cells are order-independent in effect where possible, and where order
  matters it is enforced by structure, not luck.

## Rule 8 — Share and explain your data

- **S09-C27** Any input data the notebook needs is either generated by the notebook
  or fetched by a cell in it.
- **S09-C28** No dependence on a file that exists only on the author's machine.

## Rule 9 — Design to be read, run, and explored

- **S09-C29** Committed outputs are present, so the notebook can be *read* without
  being run.
- **S09-C30** Outputs are real — never fabricated or hand-edited.
- **S09-C31** Outputs contain no secrets or identifying values.
- **S09-C32** A permissive licence and a clear README are present.
- **S09-C33** Cell-level structure allows a reader to lift out one piece and use it.

## Rule 10 — Advocate for open research

- **S09-C34** The artefact is genuinely reusable by a stranger with no context.
- **S09-C35** Claims are reproducible: a reader running the notebook should see
  behaviour consistent with the committed output, or be told why it may differ.

## Notebook JSON hygiene (added, from the community guide)

- **S09-C36** Valid `nbformat` 4.x; no corrupt or partial cells.
- **S09-C37** No empty trailing cells.
- **S09-C38** No error outputs in a committed notebook.
- **S09-C39** No `widgets` metadata referencing unavailable state.
- **S09-C40** Consistent `kernelspec` across notebooks, naming a generic kernel.
